## 1. Age gate

- **A new Google account can authenticate without a birthdate, but cannot use Discover through the reviewed application flow until a profile is saved with an adult birthdate.** `/app` requires a profile and the router sends profileless users to onboarding ([src/router.js:15](src/router.js#L15), [src/router.js:54](src/router.js#L54)). Discover independently calls `requireProfile`, which rejects missing profiles ([discover.ts:10](supabase/functions/pacemate/handlers/discover.ts#L10), [http.ts:36](supabase/functions/pacemate/server/http.ts#L36)). An existing profile holder is not asked for their birthday again.
- Onboarding requires a real calendar date, calculates age using UTC, rejects ages below 18 or above 100, and rechecks every answer before saving ([onboarding.js:17](src/onboarding.js#L17), [onboarding.js:27](src/onboarding.js#L27), [Onboarding.vue:32](src/views/Onboarding.vue#L32)). This part looks sound.
- **18+ is enforced server-side regardless of identity provider or connection mode.** `/api/me` requires a verified caller and validates a required, real birthdate before allowing any profile write ([me.ts:15](supabase/functions/pacemate/handlers/me.ts#L15), [me.ts:27](supabase/functions/pacemate/handlers/me.ts#L27)). Foundation saves also reject minors ([foundation.ts:24](supabase/functions/pacemate/server/foundation.ts#L24)). The checked-in database guard rejects null/underage birthdates on insert and update ([migration:71](supabase/migrations/20261107040000_phase1_foundation.sql#L71)). This applies to Google-created accounts too; hosted migration installation is unverified.
- Discover's shared eligibility predicate applies reciprocal gender and age-range filters when both profiles include dating ([foundation.ts:6](supabase/functions/pacemate/server/foundation.ts#L6)). It does not independently assert 18+ for every returned row; the adult invariant rests on profile writers and the database guard. `requireProfile` itself only checks existence and suspension. Thus the review does not certify old or externally inserted invalid hosted rows.
- **The adult acknowledgement is only a frontend checkbox.** Signup checks it before email or Google initiation, but Google login on `/login` has no such check and can also create a new identity ([Auth.vue:43](src/views/Auth.vue#L43), [Auth.vue:63](src/views/Auth.vue#L63), [Auth.vue:92](src/views/Auth.vue#L92)). OAuth sends no acknowledgement metadata ([auth-client.js:94](src/auth-client.js#L94)). Email signup adds a client timestamp, without server verification of acknowledgement ([auth-client.js:75](src/auth-client.js#L75)). Neither profile handler requires that timestamp or a checkbox value. Do not describe this acknowledgement as server-enforced consent. The separate birthday gate is server-enforced, based on self-reported birthdate rather than identity verification.

## 2. OAuth safety

- The authorization destination uses the configured Supabase URL, URI-encodes the provider, and sets the frontend return URL to `location.origin + '/'`. No arbitrary query-provided OAuth return URL is used ([auth-client.js:94](src/auth-client.js#L94)). Frontend configuration comes from environment variables, with no hardcoded project fallback ([supabase.js:3](src/supabase.js#L3)). Supabase's actual redirect allowlist was not inspected.
- Email login's separate `next` handling accepts any string beginning with `/`, including `//...`, and passes it to Vue Router rather than directly to `location.assign` ([Auth.vue:54](src/views/Auth.vue#L54)). This is a loose internal-path check, but is not evidence of an external OAuth redirect in the reviewed code.
- **Rework: callback acceptance is not bound to a login started in this browser.** The app uses implicit hash tokens, with no local pending-login nonce/state or PKCE verifier. Any hash containing a valid access token accepted by this project's `/auth/v1/user`, a nonempty refresh token and a user ID is persisted ([auth-client.js:55](src/auth-client.js#L55)). An unsolicited link containing another account's valid tokens can therefore sign the recipient into that account. Supabase token verification establishes token validity, not that this browser initiated the transaction. This behavior predates this WIP, whose auth-client change only adds configuration validation around OAuth.
- Forged/rejected access tokens cannot create a fresh session because `/user` is called before persistence. Missing refresh tokens or missing returned user IDs fail `saveTokens`. An unconfirmed email signup returning no tokens creates no session ([auth-client.js:32](src/auth-client.js#L32), [auth-client.js:59](src/auth-client.js#L59), [auth-client.js:75](src/auth-client.js#L75); tests [auth.test.mjs:53](tests/auth.test.mjs#L53), [auth.test.mjs:79](tests/auth.test.mjs#L79)). Existing sessions are not necessarily cleared by a failed callback.
- Not every malformed callback is rejected: refresh tokens are checked for presence only, expiry values are not strictly validated, and unknown/missing callback types become `confirmation`. A valid access token paired with a garbage refresh token can establish a session until refresh fails ([auth-client.js:33](src/auth-client.js#L33), [auth-client.js:61](src/auth-client.js#L61)). There is no explicit `email_confirmed_at` check; the client trusts Supabase to decide which accounts receive valid tokens.
- Access and refresh tokens, expiry and the full returned user object are stored as JSON in **localStorage**, under a project-URL-specific key. Passwords are not stored. Tokens remain readable by same-origin JavaScript; the opening comment saying only tokens are persisted is incomplete ([auth-client.js:4](src/auth-client.js#L4), [auth-client.js:34](src/auth-client.js#L34), [supabase.js:6](src/supabase.js#L6)). Successful callback hashes are removed, but errors leave the hash present because cleanup occurs only after callback success ([auth.js:25](src/auth.js#L25)).
- No project reference is hardcoded in the reviewed runtime auth files. The OAuth setup example targets the authorized onboarding/test project; confirm its hosted redirect allowlist independently before testing.

## 3. Location

- Only an explicit button action invokes `getCurrentPosition`. It requires a secure context, disables high-accuracy preference, allows a 60-second cached position and times out after 10 seconds. Disabling high accuracy does not guarantee the browser returns coarse coordinates ([location.js:2](src/location.js#L2), [location.js:8](src/location.js#L8)).
- The browser temporarily receives the original position, then sends only `{latitude, longitude}`, each rounded with `Math.round(value * 100) / 100`. Two decimal degrees is roughly 1.1 km in latitude, with longitude spacing dependent on latitude. No accuracy, altitude, timestamp or continuous watch is sent ([location.js:6](src/location.js#L6), [Onboarding.vue:49](src/views/Onboarding.vue#L49)). The API attaches the bearer token ([api.js:7](src/api.js#L7)).
- The handler requires POST and a verified bearer identity, but permits a member without a profile. It validates finite numeric ranges and limits requests to 10 per minute per user. It **does not enforce rounding on the server**: a custom client can submit precise coordinates ([location.ts:7](supabase/functions/pacemate/handlers/location.ts#L7), [feature-db.ts:30](supabase/functions/pacemate/server/feature-db.ts#L30)).
- Coordinates are parameters to a nearest-city SELECT over `city_coordinates`, with a 100 km cutoff. The response contains only a city or null. No submitted coordinates are written to profiles or another application table. Rate limiting does store a user/time-bucket key and hit count, not coordinates ([location.ts:12](supabase/functions/pacemate/handlers/location.ts#L12), [feature-db.ts:32](supabase/functions/pacemate/server/feature-db.ts#L32)). City-centre coordinates already exist in the lookup table.
- No reviewed application logger records coordinates or the request body: generic errors log request ID/path/method/code, and database runtime logging records connection type/deadline metadata ([http.ts:24](supabase/functions/pacemate/server/http.ts#L24), [runtime.js:18](supabase/functions/pacemate/db/runtime.js#L18), [runtime.js:44](supabase/functions/pacemate/db/runtime.js#L44)). This cannot establish retention in hosted infrastructure/database query logs, which were not inspected. Therefore “not stored or logged anywhere” would be too broad.
- **No external geocoding provider is called.** There is nevertheless an external HTTP call to the configured Supabase Auth `/auth/v1/user` to verify the bearer, followed by database operations ([supabase.ts:12](supabase/functions/pacemate/server/supabase.ts#L12), [feature-db.ts:4](supabase/functions/pacemate/server/feature-db.ts#L4)). There is no Google Maps/geocoding API fee introduced by this implementation. Edge execution, Auth, database and network usage consume the project's applicable Supabase resources; exact monetary cost cannot be determined from this repository and no pricing/hosted lookup was performed.
- Onboarding preserves an existing home city and fills current city; Discover fills only a draft search city, requiring Search to apply it ([Onboarding.vue:53](src/views/Onboarding.vue#L53), [Discover.vue:29](src/views/Discover.vue#L29), [Discover.vue:43](src/views/Discover.vue#L43)). Manual fallback looks fine.

## 4. Onboarding and Discover

- The final save still uses the existing `PUT /api/me`, bound to the initiating user, followed by Discover navigation. It does **not** call `PUT /api/foundation` ([Onboarding.vue:37](src/views/Onboarding.vue#L37)). The previous onboarding also used `/api/me` (parent commit comparison).
- The payload contains legacy profile fields, not `connection_modes`, Foundation sport intensity, country or language fields ([onboarding.js:44](src/onboarding.js#L44)). Existing Foundation handlers remain intact and preserve explicit multi-mode saves through their own endpoint ([handlers/foundation.ts:15](supabase/functions/pacemate/handlers/foundation.ts#L15), [handlers/foundation.ts:23](supabase/functions/pacemate/handlers/foundation.ts#L23)).
- Foundation compatibility depends on existing database triggers: on new legacy inserts, relationship/casual goals become dating, friends becomes friendship, and all other goals become training_partner. Legacy sports synchronize into `user_sports` ([migration:68](supabase/migrations/20261107040000_phase1_foundation.sql#L68), [migration:86](supabase/migrations/20261107040000_phase1_foundation.sql#L86)). Therefore onboarding does not support selecting multiple connection modes directly. In particular, “Open to all” becomes training_partner on insertion, not all three modes. This mapping is pre-existing, not introduced by the Discover diff. `/api/me` updates do not overwrite existing Foundation connection modes because those fields are absent from its update values ([me.ts:52](supabase/functions/pacemate/handlers/me.ts#L52)).
- Compared with the parent, onboarding replaces split birthday inputs with a date input, separates questions, adds a final unsaved preview and full revalidation, adds location suggestions and account/unmount protections, and removes the prior work-style/travel questions. Omitted trip fields preserve saved trips on update ([me.ts:49](supabase/functions/pacemate/handlers/me.ts#L49)); a new user can no longer supply travel during this flow.
- **Discover's candidate SQL, eligibility, limit and ordering are unchanged by this WIP.** The only handler change caches the viewer Foundation shape, computes each candidate shape once, and adds `sharedConnectionModes` as their intersection ([discover.ts:36](supabase/functions/pacemate/handlers/discover.ts#L36)). It does not sort by compatibility score. Profile answers and applied city filters still affect results through existing predicates ([discover.ts:26](supabase/functions/pacemate/handlers/discover.ts#L26)). Location permission alone does not alter candidates.

## 5. Setup document

The document contains these Google Cloud/dashboard steps, expressed here as a complete inventory rather than instructions performed during review:

1. Choose the intended Supabase project; open Authentication provider settings and enable Google with its OAuth client ID and secret ([setup:9](GOOGLE_SIGNUP_SETUP.md#L9)).
2. In Google Cloud, configure a **Web application** OAuth client and put the callback supplied by that Supabase project into its authorized redirect URIs. The document supplies the current workspace example and says to substitute the test project's callback when applicable ([setup:9](GOOGLE_SIGNUP_SETUP.md#L9), [setup:11](GOOGLE_SIGNUP_SETUP.md#L11), [setup:17](GOOGLE_SIGNUP_SETUP.md#L17)).
3. Configure Google's consent screen and add test accounts if the audience is restricted to test users. Keep the client secret in Supabase provider settings, outside frontend variables/source control ([setup:17](GOOGLE_SIGNUP_SETUP.md#L17)).
4. In Supabase Auth URL Configuration, allow `http://localhost:5173/` and `http://127.0.0.1:5173/`, add the actual hosted frontend return URL and set the appropriate Site URL ([setup:19](GOOGLE_SIGNUP_SETUP.md#L19), [setup:26](GOOGLE_SIGNUP_SETUP.md#L26)).
5. Outside the dashboards, configure the intended project's frontend URL and publishable key in ignored `.env.local`, restart Vite, and later deploy the updated Edge Function under separate authorization ([setup:28](GOOGLE_SIGNUP_SETUP.md#L28), [setup:45](GOOGLE_SIGNUP_SETUP.md#L45)). The six manual checks cover availability/retry, acknowledgement, return/session/onboarding, minor rejection, save/relogin and consent cancellation ([setup:32](GOOGLE_SIGNUP_SETUP.md#L32)).

Missing or insufficiently explicit for a reproducible setup checklist:

- Selecting/creating the Google Cloud project, completing the consent-screen application identity/support/contact fields, choosing the audience and publishing/test status, and saving the OAuth client/provider configuration. “Configure the consent screen” compresses all of this into one sentence ([setup:9](GOOGLE_SIGNUP_SETUP.md#L9), [setup:17](GOOGLE_SIGNUP_SETUP.md#L17)). Exact current dashboard labels and conditional verification requirements were not checked, consistent with the prohibition on hosted contact.
- Explicit authorized JavaScript origin guidance for the Google Web client, distinguishing frontend origins from the Supabase redirect URI. The document only specifies authorized redirect URIs. This code redirects through Supabase and does not embed Google's browser SDK, so the omission alone does not prove a broken login ([auth-client.js:94](src/auth-client.js#L94)).
- A clear separation of the bypassable signup acknowledgement from the server birthday rule; `/login` can create a new Google identity without acknowledgement ([Auth.vue:46](src/views/Auth.vue#L46)).
- The existing Foundation migration/trigger dependency for legacy onboarding mode/sport synchronization and database adult enforcement. “No migration is added” is accurate for this WIP, but does not establish the prerequisite schema is installed ([setup:45](GOOGLE_SIGNUP_SETUP.md#L45), [migration:68](supabase/migrations/20261107040000_phase1_foundation.sql#L68)).
- A precise limitation on “no external geocoding call”: Supabase Auth and database access still occur, and server-side rounding is absent ([setup:43](GOOGLE_SIGNUP_SETUP.md#L43), [location.ts:8](supabase/functions/pacemate/handlers/location.ts#L8)).

The callback/frontend-return distinction, secret handling, environment configuration, location permission explanation and explicit statement that hosted configuration is unverified are all useful and correct. This review does not claim consent-screen policy URLs or verification are universally required; that depends on the actual Google configuration and was not inspected.
